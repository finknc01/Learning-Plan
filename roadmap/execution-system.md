# Execution System

This workflow is designed to make a year-long technical plan easier to start, resume, and sustain without turning every unfinished item into mental backlog.

## Core rule

Optimize for **starting and returning**, not for perfect consistency.

At the beginning of each two-week block, activate no more than three things:

1. **NOW — one primary lab mission**
2. **NEXT — one supporting concept**
3. **EVIDENCE — one artifact or milestone proving the work**

Everything else is **Later**.

## Now → Next → Later

### NOW
One physical action that can be started immediately.

Good:

> Open Fabric-Faultline Mission 01 and capture `ip addr` and `ip route` from both namespaces.

Too vague:

> Study networking.

### NEXT
One concept or resource required to understand NOW.

This keeps theory attached to a concrete reason for learning it.

### LATER
Interesting tools, certifications, optimizations, side projects, and rabbit holes belong here until they are relevant to the active block.

Capture them instead of switching tasks mid-session.

## Session sizes

Do not wait for the perfect multi-hour study window.

### 15-minute ignition
Use when starting is the hard part.

Success means:

- open the current repository/mission
- orient to the last breadcrumb
- inspect, run, or change one thing
- write the next action before stopping

### 45-minute standard session

```text
5 min  — orient
30 min — hands-on work
10 min — evidence, notes, commit, breadcrumb
```

### 90-minute deep session
Use when attention is naturally strong.

Run two focused work periods with a short break. Stop with the environment documented and the next action obvious.

## Minimum viable week

The target remains **8–10 focused hours per week**, but continuity should not depend on hitting that number every week.

A minimum viable week is:

- three short study sessions
- meaningful progress on one primary mission
- one written restart point

That week still advances the plan.

**Do not double the next week's workload to compensate.** Resume the current work and preserve momentum.

## Breadcrumb every session

Before stopping, record:

- **What I just proved:** one sentence
- **What is broken or unknown:** one sentence
- **Next physical action:** one concrete instruction
- **What to reopen:** file, repo path, command, dashboard, diagram, or documentation page

The goal is to make returning after several days cheap.

## Use novelty without abandoning the roadmap

If one mode stops holding attention, change the activity while staying inside the same objective:

```text
read
 ↓
build
 ↓
break
 ↓
diagnose
 ↓
diagram
 ↓
write
```

The story-driven labs are the default source of novelty. Prefer moving to the next incident or experiment over starting an unrelated tool or course.

## Research stop rule

Research is complete enough when there is enough understanding to perform the next safe experiment.

At that point, **run the experiment**.

Do not keep reading merely because more documentation exists.

## Completion rule

For each two-week block, prioritize:

1. **Primary hands-on mission(s)**
2. **Concepts required to understand them**
3. **Evidence / milestone artifact**
4. **Optional course depth, certifications, polish, and extra tools**

If time is limited, trim item 4 first.

## Portfolio-quality does not mean perfect

An artifact is complete when it clearly proves the intended skill.

Avoid repeatedly redesigning READMEs, dashboards, diagrams, or scripts unless the change:

- teaches something new
- fixes a real technical problem
- materially improves reproducibility
- materially improves employer-facing evidence
